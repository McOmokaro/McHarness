# Pi (badlogic/pi-mono) — Source Dossier for McHarness

Canonical repo: https://github.com/badlogic/pi-mono — "Pi is a minimal, extensible agent harness that you can make your own." Npm namespace `@earendil-works/pi-*`. Known upstream of OpenClaw. Audit is against a shallow clone of `main`.

## REPO MAP
`packages/` (all under `@earendil-works/pi-*`):
- **agent** (~6 files): the framework-agnostic agent loop (`agent-loop.ts`, `types.ts`, `agent.ts`, `stream-fn.ts`). The crown jewel; no coding-agent deps.
- **ai** (`pi-ai`): provider layer — messages, streaming, tool validation, `normalizeContext`, `EventStream`. All provider normalization lives here.
- **coding-agent**: the product "Pi" — `src/core/` (~60 files: session-manager, agent-session, compaction/, extensions/, skills.ts, prompt-templates.ts, system-prompt.ts, model-registry, tools/), `src/modes/` (rpc, json, print…), `src/cli/`, `src/extensions/` (codemode, mcp, tool-search, llama).
- **tui**: terminal framework (`tui.ts`, `layout-node.ts`, `components/`, editor, autocomplete, kill-ring, undo-stack, alt-screen).
- **mcp**, **codemode**, **durable**, **env**, **telemetry**, **chord**, **evals**: satellite packages — MCP plumbing, script-calling-tools, durable tool effects, env management, telemetry.

## AGENT LOOP
Entire loop is one file: `packages/agent/src/agent-loop.ts` (~950 lines) + `types.ts` (~540). `runLoop` is a **doubly-nested while**: inner loop runs while there are tool calls or steering messages; outer loop drains follow-up messages after the agent would otherwise stop. Every side-effect-free extension point is a callback on `AgentLoopConfig` (`packages/agent/src/types.ts:193`): `convertToLlm` (AgentMessage[]→LLM Message[], required), `transformContext`, `prepareRequest`, `finishTurn` (returns `{action:"continue"|"end"}`), `prepareNextTurn` (can swap context/model/thinkingLevel mid-run — how compaction works), `getSteeringMessages`, `getFollowUpMessages`, `beforeToolCall`/`afterToolCall`, `getApiKey`.

Message flow: stream events (`text_delta`, `toolcall_delta`, thinking variants) mutate a partial `AssistantMessage` pushed into `context.messages` and mirrored via `message_update` events. Tool dispatch (`executeToolCalls`) supports parallel (preflight sequentially, execute concurrently via thunks, `Promise.all`) and per-tool `executionMode: "sequential"` override; `beforeToolCall` can `{block, reason, terminate}`; `afterToolCall` field-wise overrides result content/details/isError/terminate; `terminate: true` on **every** result in a batch ends the run early. Notably disciplined: `stopReason === "length"` fails **all** tool calls in the message (`failToolCallsFromTruncatedMessage`) because streamed JSON salvage may silently truncate arguments — the model is told to re-issue. `runToolCall` exposes the exact same validate→hook→execute→finalize path for nested tool calls (permission checks apply uniformly).

What's deliberately absent: no sub-agents, no plan mode, no planner/executor split, no built-in memory, no hardcoded approval UI. The loop is a pure state machine; everything app-level is injected via config callbacks or implemented above it in `coding-agent/src/core/agent-session.ts`.

## EXTENSIONS & PACKAGES
Docs: `packages/coding-agent/docs/extensions.md`. Extension = default-export factory receiving `ExtensionAPI` (`pi`), loaded from `~/.pi/agent/extensions/` or project dirs via **jiti** (TS with no build step). API surface: `pi.on()` (event bus, ordered, unsubscribe fn returned), `registerTool/Command/Shortcut/Flag/Provider/McpServer/VirtualModel`, `sendUserMessage/sendMessage`, `appendEntry`, session control, renderer registration, `pi.events` inter-extension bus.

Key event contract (from extensions.md + `src/core/extensions/types.ts`): lifecycle events — `before_agent_start` (mutate prompt sections or replace whole prompt; distinguishes `messageType: "user"|"custom"`), `message_end` (replace finalized message), `tool_call` (mutate args / `{block, reason}` — the approval-gate example in docs uses MCP `annotations`: `readOnlyHint`, `destructiveHint`…), `tool_result` (composable redaction; handlers see prior changes), `provider_stream_event` (read-only earliest parsed event), `context` / `context_with_system` (transformation hooks Pi restores state around), `turn_end`/`agent_before_settle` (can return `continue: true` for one more request — guarded against infinite loops), `agent_settled` (notification-only), `session_start`/`session_shutdown`, `cache_warming_decision`, `project_trust` (runs before untrusted project extensions).

Tool exposure model is unusually rich: `exposure: "direct" | "model-only" | "codemode" | "deferred" | "hidden"`; namespaces with `aliases`/`instructions`; `prepareLoadout(loadout)` lets an orchestrator tool rewrite sibling declarations; `reachesTools(input)` declares which tools a call may transitively reach (used by codemode/tool_search and late-connecting MCP servers). Nested tool calls via `ctx.executeTool` get IDs `<parent>/<n>`, don't add transcript entries, keep a **bounded** `nestedCalls` record (8KiB arg / 32KiB result caps, ≤256 calls), and roll up usage at every depth. File mutations go through `withFileMutationQueue()`.

Skills (`docs/skills.md`, `core/skills.ts`), prompt templates (`core/prompt-templates.ts`), themes, and packages (`docs/packages.md`, `core/package-manager.ts`, `pi-manifest.ts`) are all resources injected into the system prompt's **sections** — see session storage below.

## SESSION STORAGE
`docs/session-format.md`; impl `core/session-manager.ts`. **JSONL** at `~/.pi/agent/sessions/--<path>--/<timestamp>_<uuid>.jsonl`. First line `SessionHeader` (v3, optional `parentSession` for forks); every entry has `type`, `id`, `parentId`, ISO `timestamp` — a **tree**, not a list (v2+), enabling in-place branching (`/tree`, `branch_summary` entries with LLM summaries of abandoned paths). Entry types: `message`, `model_change`, `thinking_level_change`, `usage` (non-context, e.g. `cache_warm`), `compaction` (summary + `firstKeptEntryId` + full system-prompt/tool checkpoint), `context_edit` (append-only replacement/null-out of an earlier entry's model-visible content; branch-relative), `custom` (extension state, excluded from context), `custom_message` (extension content that IS sent to the model), `label`, `session_info`.

Crucial design: **system messages carry prompt + tool loadout as replayable deltas** — the first request persists a system message with all prompt `sections` and tool declarations; later changes append system messages patching `sections` by name (null removes) and `toolsAdded`/`toolsRemoved`. Replaying yields current state; there is no separate prompt-state entry. This mirrors `declareToolChanges` in the loop (which computes the diff against `context.tools` each turn). Context rebuild: `buildContextEntries()` walks leaf→root honoring compaction; `buildSessionProjection()` applies `context_edit`s; `buildSessionContext()` produces the LLM list.

## TUI
`packages/tui/src`: own layout engine (`layout.ts`, `layout-node.ts`), component model (`components/`, `editor-component.ts`), foregrounding infra: `stdin-buffer.ts`, `keys.ts`/`keybindings.ts`, `kill-ring.ts`, `undo-stack.ts`, `word-navigation.ts`, `autocomplete.ts`, `fuzzy.ts`, alt-screen + search (`tui-alt-screen.ts`, `alt-screen-search.ts`, `wheel-scroll.ts`), `terminal-image.ts` (Sixel/iTerm), OKLab color (`oklab.ts`, `colors.ts`), native platform shims (`native-platform.ts`). Renderer-agnostic design: extensions register `renderCall`/`renderResult` per tool and the same rendering feeds interactive transcript **and HTML exports** (`core/export-html/`). `ctx.ui` abstracts dialogs/notifications/widgets so the same core runs headless in RPC/JSON/print modes (`ctx.mode`, `ctx.hasUI` guards).

## RPC / SDK / MODES
`docs/rpc.md`: `pi --mode rpc` = JSONL on stdin/stdout. Four record families: commands (with optional `id` for correlation), `response` records, session events, extension-UI records. `data.disposition` on `prompt` tells whether a run started; clients wait for **`agent_settled`** (not `agent_end`) because retries/compaction/steering can follow a run. Careful framing spec: split on LF only, warn that Node `readline` wrongly splits on U+2028/U+2029 inside JSON strings. ~30 commands (get_state, set_model, compact, fork/clone, get_tree…). SDK (`docs/sdk.md`) is the in-process variant; same `AgentSession` core (`core/agent-session.ts`, `core/sdk.ts`) backs CLI, interactive TUI, RPC, JSON, and print modes — extensions load in all modes, guarded by `ctx.hasUI`.

## TOOLS
Built-ins in `core/tools/`: `read.ts`, `edit.ts` (+`edit-diff.ts`), `write.ts`, `bash.ts`/`powershell.ts`, `grep.ts`, `find.ts`, `ls.ts`, plus `truncate.ts`, `output-accumulator.ts`, `file-mutation-queue.ts`, `tool-definition-wrapper.ts`. Tool shape = `AgentTool` (types.ts:466): TypeBox schema, `label`, optional `prepareArguments` (pre-validation compat shim), `outputSchema` → `structuredContent` (machine-readable, never sent to model; codemode scripts consume it), `isError`/`terminate`/`replay` ("never"|"safe" for durable-effect recovery), `executionMode`. Custom tools register via `pi.registerTool()`; `codemode` exposure lets scripts call them through `ctx.executeTool` without model-facing declarations.

## CROWN JEWELS
1. **Config-callback loop** (`agent-loop.ts` `AgentLoopConfig`): the whole agent is one function + ~8 injectable callbacks; no class hierarchy, no plugin registry inside the loop. → Rust: `LoopHooks` trait with `async fn` hooks on a `run_loop(prompts, ctx, hooks, signal)` free function.
2. **Queue drain points** (`getSteeringMessages`/`getFollowUpMessages` + `QueueMode "all"|"one-at-a-time"`): user messages injected between turns; steering mid-turn, follow-up after stop, no thread/queue machinery in the loop. → Rust: `mpsc::Receiver<Msg>` polled at two well-defined points.
3. **Replayable transcript deltas**: system messages as prompt/tool patches (`declareToolChanges`, session-format system messages). Cache-friendly, resumable, zero extra state files. → Rust: `enum SystemDelta { Sections(BTreeMap<String,Option<String>>), ToolsAdded(..), ToolsRemoved(..) }` appended to history.
4. **Tree-structured JSONL sessions** with `id/parentId`, compaction checkpoints, and append-only `context_edit`/`branch_summary`. → Rust: serde `SessionEntry` enum, `Vec<Entry>` append-only file, leaf-walk rebuild.
5. **Truncation safety**: `stopReason=="length"` fails every tool call in the batch with a "re-issue" error (`failToolCallsFromTruncatedMessage`). Cheap fix for a silent-corruption class. → Rust: 10-line match on `StopReason::Length`.
6. **`structuredContent` + `details` split** on tool results: model sees `content`, UI/scripts see structured data; `outputSchema` enforced. → Rust: `ToolResult { content: Vec<Block>, details: Value, structured: Option<Value> }`.
7. **Termination by unanimous `terminate`** across a tool batch + `beforeToolCall {block}`/`afterToolCall` override hooks: cancel/stop flows are pure data, no out-of-band channels. → Rust: `all(results.iter().map(|r| r.terminate))`.
8. **Mode-uniform core with capability flags** (`ctx.mode === "tui"`, `ctx.hasUI`): same session/tools/extensions run interactive, RPC, JSON, print. → Rust: `Mode` enum + `Ui` trait (TUI impl / no-op impl) threaded through context.

## WHAT NOT TO COPY
- **jiti/TS extension loading**: dynamic transpiled in-process code = heavy runtime coupling and a trust problem Pi itself documents. Rust equivalent should be WASM or a subprocess protocol (the RPC mode is the better transplant).
- **Declaration merging** (`CustomAgentMessages`) for extensible message unions — TS-only trick; use an enum with `Custom(CustomPayload)` instead.
- **Global event-order contracts** (extension handlers run in load order, compose via mutation): hard to verify, race-prone; prefer explicit hook pipelines returning values (Pi's `before/afterToolCall` style is better than its `tool_result` handler-chain style).
- **`provider_stream_event` exposure**: hands raw provider events to extensions before normalization — fragile across provider versions.
- **Promise-based parallelism with shared `context.messages` mutation**: the loop mutates the context array in place across concurrent thunks; safe only via JS single-threading. Rust needs ownership discipline (`Arc<Mutex<Transcript>>` or message-passing).
- **Over-minimal gaps**: no built-in sub-agent/primitive, no plan mode, no sandboxing story beyond `withFileMutationQueue` and trust prompts — multi-agent harnesses will need to add these *above* the loop, exactly as Pi's `agent-session.ts` layer does.
